博客服务层迁移：五个动态部件的搬家与升级
Yiwei Zhang 2026年11月14日 晚上
1.8k 字 15 分钟 0 次   0 人   0 条
1794670800000

本文最后更新于：2026年11月14日 上午

博客的静态页面托管在 GitHub Pages 上没问题，但它的五个"动态器官"——评论、访问统计、图床、一言、壁纸配对——全部长在旧 NAS 上：旧机一死，博客立刻变哑巴。本文记录这五个部件逐个搬到新虚拟机并全部升级到最新版的完整过程，包括每个部件的对账口径和搬家过程中挖出的旧栈暗病。

背景：博客的命脉在旧 NAS 上

博客表面上是纯静态站，实际上有五个部件每时每刻在和旧服务器打交道：读者在文章页发评论（评论系统，数据库是五年前装的 MongoDB 3.6）、每次访问被记录（统计系统）、每一张配图从旧机图床加载（六年来积累四十余 GB、文章里一万七千余处引用）、页脚随机短句（自建一言）、首页背景视频（壁纸配对 API）。旧 NAS 退役倒计时启动后，这五个部件就是博客与新平台之间仅存的脐带——不断干净，博客就不能算迁移完成。

目的

三条硬指标：五个部件全部运行在新栈；数据零丢失（评论一条不少、统计一个事件不丢）；版本全部升到最新——五年没升级的账一次还清。一条软指标：搬家过程中顺手治好"一直坏着但没人知道"的暗病。

方案选择：逐个搬家而不是整批搬运

备选方案有二：把旧虚拟机整体镜像搬到新平台（快，但把 EOL 系统和五年积弊原样带走，违背升级初衷）；或逐个部件新装最新版 + 数据迁移（慢，每件都要对账，但每搬一件就还一件技术债）。

选择后者的决定性理由：旧栈的 MongoDB 3.6 是连官方支持都结束多年的版本，评论系统落后一年半，统计系统落后两个大版本——整批搬运等于把这些定时炸弹一起搬进新家。且新栈的"迁移即升级"在第一个部件（评论）上验证可行后，后面每个都是复制流程。

实施：五部件各自的搬法

评论系统（最深的器官）：数据库 MongoDB 3.6 直升 8.x 跨五个大版本，服务端一年半的版本差。搬家后连环挖出四个暗病，个个都是"一直坏着没人知道"：登录签名钥在旧栈是静默借用数据库密码的，环境变量对齐时被带走导致管理端完全登不上；服务端每个请求都替访客去境外拉一份社交登录列表，全站 API 被拖慢；存量头像指向境外源；反代头没带端口导致管理端把请求打到不存在的默认端口。逐一修复后，管理端从"数秒到超时"降到两秒内。前端评论组件同步改走自托管构建——此前一次主题升级曾因第三方 CDN 换构建格式把评论区打断，这次彻底断了这个依赖。

访问统计（数据最密的器官）：跨两个大版本升到最新，四十六万事件全量落位。两个关键动作：一是新版会话模型会重建旧数据，看起来"少了"——逐表核对确认是合并而非丢失；二是切换缺口的补同步——新栈上线用的是几天前的备份，切换前最后几天的新访问还留在旧库，按时间区间从旧库导出、跨版本手工映射列名、幂等写回，切换期数据一条不丢。

图床（体积最大的器官）：四十余 GB 走局域网管道直传，难点在引用切换：一万七千余处地址全量替换。方法上先扫"双端口形态"变体（垃圾替换会滚雪球的根源），替换后全站产物扫描归零确认，最后给图床补跨域头让搜索索引等跨域场景打通。

一言（最轻的器官）：版本已是上游终版，真正的问题是语料同步源被墙——一万一千余句几个月没更新。换镜像源即恢复，服务零改动。

静态站本体：Hexo 跨大版本升级，沙箱全量生成对比两千余页逐页一致后才上线；站内搜索从 27MB 单文件索引重构为分片索引（详见 Fluid -48）；发布流收敛为一条命令。

结果：对照目的验收

  • 五部件全部在新栈：是，且旧机对应服务已全部停机
  • 数据零丢失：评论逐条计数一致；统计全量事件核对一致外加缺口补回；图床逐字节同步
  • 版本最新：评论一年半、统计两个大版本、数据库五个大版本、静态站一个大版本——全部到位
  • 暗病红利：评论系统四个、统计一个同步源、搜索一个境内加载问题——搬家挖出的病比平时一年遇到的都多

超额达标。终极验证也做了：旧服务器此刻拔电，博客一个字节不受影响——这句"不受影响"不是感觉，是逐项停机后全站回源验证过的结论。

尾声

五个器官搬完留下的方法论四条：对账用绝对数（"差不多"不叫对账）；切换期数据缺口要显式补（最容易被忘的数据）；暗病会在搬家时暴露（环境对齐的过程就是体检）；前端引用切完要回源验证（CDN 缓存会骗人）。
