NAS 迁移收官：从 J3455 到 PVE 虚拟化全栈
Yiwei Zhang 2026年11月14日 晚上
2.7k 字 23 分钟 0 次   0 人   0 条
1794659400000

本文最后更新于：2026年11月14日 上午

五年前用 J3455 攒的 NAS 到了退役的时候：CPU 撑不住、内存加不动、系统盘还是 USB 的。这次升级不是换台机器，而是把"一台机器什么都干"拆成"一台物理机跑八个虚拟机，存储归存储、应用归应用、网关归网关"。服务在搬家的同时全部升到最新版，旧机器上确认迁完的部分已经全部停机。本文是 NAS 硬件升级方案 的收官记录。

为什么要推倒重来

老 NAS 是 2021 年装配的 J3455 平台，五年下来每一层都到了瓶颈：

  • CPU：J3455 是四核四线程的 Apollo Lake 低功耗处理器，跑 Ubuntu + KVM + OMV + Docker 的组合早就力不从心，博客服务一忙全家都卡
  • 内存：DDR3L 12GB，跑一个 OMV 虚拟机加一个应用虚拟机就见底，多开任何东西都要权衡
  • SATA：四个原生口加两个 M.2 转接加一个 USB，七个口已经是这台机器的物理极限，六块机械盘 + 两块固态塞得满满当当
  • 系统盘：系统装在 USB SATA 盘上，长期运行存在连接和供电的稳定性隐患，这五年一直是心里的一根刺
  • 架构：所有服务挤在一个系统里，升任何一个组件都要掂量全局，Docker 网络、数据库端口、反向代理互相缠绕，动一发牵全身

升级方案几经修订（详见方案篇），最终定为 AM5 平台 + Proxmox VE 虚拟化：Ryzen 7 9700X、B850M 追击炮、两条 16GB DDR5、两块 1TB SATA SSD 组 ZFS mirror 做虚拟化层存储，六块 6TB 机械盘后续整体搬迁。不买显卡，AI 需求走外部 API。

装机过程并不顺利：先是内存兼容性破案——三星颗粒的条子在这块板上怎么都点不亮，换金士顿一次通过；中途还换过一次主板。最终新平台以金士顿 32G @4800 稳定运行至今，PVE 9.2 + ZFS RAID1 一次装成。

迁移策略：装一个、切一个、拆一个

迁移最大的风险是"搬家当天全站停摆"。这次采用的策略把风险拆散了：

旧机器不停。 老的应用虚拟机先把数据盘切到机械盘备份组上继续跑，系统盘拔掉都无感知。新机器这边逐个服务搭建，搭好一个、验证一个、路由器端口转发改向一个，出问题改回转发就是回滚，单服务回退窗口 30 秒。

数据全程带对账。 每一项数据迁移都做数量级核对：评论一千零二条逐条对齐、访问统计四十六万事件百分百落位、网盘一百零四个文件连密码哈希一起搬、家庭相册三库全量核对。中间还补过一次统计缺口——新旧切换的时间差里产生的七千多条访问数据，跨版本手工合并回新库。

迁移即升级。 不搬旧版本，全部直接上新版：评论系统 1.31 → 1.43、统计 2.x → 3.5、MongoDB 3.6 → 8.3、PostgreSQL 15 → 18、Hexo 7.2 → 8.1。五年欠的版本账一次还清。

终态：一台物理机，八个虚拟机

新平台的虚拟机按职责切分，VMID 就是 IP 尾号，终身免查表：

VMID 职责 内容
110 存储层 OMV 8，等六块机械盘搬入后接管全部文件服务
120 应用层 博客全家桶：图床、评论、统计、一言、公式识别等 17 个容器
130 网关层 nginx 单端口 SNI 入口 + WireGuard 回国代理
140 观测层 Kuma 拨测 + Prometheus 指标 + Grafana 面板
150 家庭层 Nextcloud 35 + 家庭相册服务
160 开发层 开发机，远程 SSH 直达
170 支撑层 按需启动的图形排障机
9000 模板 Ubuntu 云镜像模板，克隆即用

这套分层立了几条纪律：数据库放 SSD 虚拟盘、大文件归机械盘、每个容器配 discard=unmap 让 fstrim 穿透释放、虚拟机 CPU 显式指定 x86-64-v3（默认的 kvm64 缺 AVX 指令集，MongoDB 5+ 会直接崩）。最后这条是踩过坑的：全家克隆出来的虚拟机统一补的课。

公网入口从旧机器的三十多个转发端口，收敛为四个：单一 HTTPS 端口按子域名分发全部 web 服务（详见网关篇）、一个代码仓 SSH、一个 WireGuard UDP、一个开发机 SSH。暴露面缩了将近九成。

博客与服务的新地址

所有服务从"IP + 裸端口"搬到了子域名，全部经网关 61213 端口按 SNI 分发：

服务 旧地址 新地址
图床 uipv4:330xx img.zywvvd.com
评论 Waline uipv4:330xx waline.zywvvd.com
统计 Umami uipv4:330xx umami.zywvvd.com
一言 uipv4:330xx hitokoto.zywvvd.com
公式识别 uipv4:330xx formula.zywvvd.com
PV/UV 壁纸 uipv4:330xx pvuv.zywvvd.com
云盘 Nextcloud uipv4:330xx files.zywvvd.com
家庭相册 uipv4:160xx family.zywvvd.com
代码仓 OneDev uipv4:330xx git.zywvvd.com
状态页 Kuma uipv4:330xx status.zywvvd.com

博客侧同步做了全量切换：文章源码里一万七千多处图床引用批量替换成新域名，评论组件、统计脚本、一言接口、壁纸配对 API、搜索索引全部指向新栈。做完这步之后做了专项验证——生产页面上旧机器的引用清零。旧机器现在哪怕直接拔电，博客一个字节都不受影响。

旧机下线

确认迁移完成的服务全部停机：老评论系统连同它的 MongoDB、旧一言和 Redis、旧 Kuma、公式识别、PVUV 统计、图床上传器，OMV5 上的旧 Nextcloud 三容器、家庭相册旧套件六容器、已决定弃用的 SyncTV，以及 crontab 里的两个定时同步脚本。停机后跑了一轮全站验证，十项核心服务全绿。

老机器上还活着的只剩三类，都刻意保留：音乐库、网盘、记事本这几个还没迁真实数据的小服务；OMV5 本体承担的备份链；以及公网 DDNS——它是整个公网入口的命脉，等搬盘批次迁进网关虚拟机。

版本审计

收官时顺手把全栈版本过了一遍：PVE 9.2、Docker 29.9、Kuma 2.5.11、Grafana 13.3、Prometheus 3.16、Waline 1.43、Umami 3.5、MongoDB 8.3、Redis 8、PostgreSQL 18、Hexo 8.1、Nextcloud 35.0.2——全部是各家当前最新可用版。唯一的历史欠账是 Nextcloud 底下的 MariaDB 10.6 已过支持期，排进了下一个升级窗口。

尾声

五年前攒第一台 NAS 时，图的是一台机器解决所有需求；五年后拆成八个虚拟机，图的是每个需求都能单独折腾。老机器教会我"什么都能跑"，新平台教会我"跑坏了怎么救"——这大概是这次升级真正买到的东西。
