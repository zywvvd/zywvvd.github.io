NAS 硬件升级方案
Yiwei Zhang 2026年10月9日 下午
8.4k 字 71 分钟 0 次   0 人   0 条
1791534000000

本文最后更新于：2026年10月12日 下午

2021 年装配的 J3455 平台 NAS 服役五年，CPU、内存、SATA 扩展和系统盘都已经到瓶颈。本文记录 2026 年升级方案：换用 AM5 新平台，引入 Proxmox VE，同时把本地大模型推理改为 API-first，暂不购买显卡。
系列前置文章：NAS 硬件调研、NAS 硬件采购配置记录、NAS 总结篇。

2026-10-12 方案修订

最初方案按「半高显卡 + 大内存本地推理」设计，经过对预算、散热、显存上限、模型能力和使用收益的重新评估，最终改为：

核心结论：

  • CPU 选 Ryzen 7 9700X：8C/16T 足够，散热和噪音优先。
  • 不买 GPU：半高显卡贵、显存有限、散热有风险，能跑的模型上限也一般；当前收益不如外部 API。
  • 不买大内存：现有 2×16GB 若是 DDR5 UDIMM 就直接复用，32GB 对当前服务足够。
  • 不买 NVMe：两块闲置 1TB SATA SSD 先组 PVE 系统镜像，容量和可靠性都比现在的 USB 系统盘好得多。
  • 电源必须换：旧 250W FLEX 不再适合 9700X + 6 块机械盘 + 未来扩展；但新电源长度必须实测机箱，不能默认 170mm 长卡能放下。

配置思路

  • 保留现有宝藏机箱、6 块 6TB 机械盘、硬盘仓风扇和主板仓风扇。
  • 新平台能稳定承载 Proxmox VE、OMV 存储虚拟机、Docker 应用虚拟机和 AI API 网关。
  • 至少凑出 10 个 SATA 接口，迁移 6 块机械盘并保留扩展空间。
  • 正式联网使用有线网口，Wi-Fi 只作为装机临时联网或应急备份。
  • 不把预算花在本地 GPU 推理上，优先保证存储可靠性、散热余量和迁移安全。
  • 迁移期间保留旧系统盘和至少一块备份盘，保证可以回滚。

现有平台的主要瓶颈：

  1. J3455 是 4C/4T 低功耗 Apollo Lake，Ubuntu + KVM + OMV + Docker 已经力不从心。
  2. SATA 已经是 4 原生 + 2 M.2 转接 + 1 USB 的极限状态。
  3. DDR3L 12GB 内存无法承载更多虚拟机和应用。
  4. PCIe 2.0 x1 空置，无法扩展万兆网卡或更实用的存储控制器。
  5. 系统盘走 USB SATA，长期运行存在连接和供电稳定性隐患。

平台选型

为什么选 AM5

  • AMD 已确认 Zen 6 桌面版继续使用 AM5，后续仍有换 CPU 的机会。
  • AM5 平台的 SVM/IOMMU/PCIe 直通等虚拟化能力完整，适合 Proxmox VE。
  • 对 NAS 常驻负载而言，多核性价比和平台寿命比消费级 iGPU 更重要。
  • 短板也要承认：消费级平台没有理想的 ECC 内存生态，可靠性主要靠备份、UPS、ZFS 冗余和迁移流程补强。

CPU 选择

型号 规格 TDP/PPT 结论
Ryzen 7 9700X（最终选择） 8C/16T Zen 5 65W / 88W 散热、噪音和性能的平衡点；对 PVE + OMV + App + AI Gateway 足够
Ryzen 9 9900X 12C/24T Zen 5 120W / 162W 多核余量更大，但满载发热接近 9700X 的两倍，小机箱散热压力明显增加
Ryzen 9 9950X 16C/32T Zen 5 170W / 230W 对这个机箱和用途过热、过剩，不适合默认功耗运行

CPU 可靠性与散热判断

  • 可靠性：Zen 5 桌面平台用于 Homelab 已比较成熟。主要风险不在 AMD CPU 本身，而在消费级主板 BIOS 兼容性、非 ECC 内存、机箱散热余量和电源质量。
  • 散热差距：9700X 是 65W TDP / 88W PPT；9900X 是 120W TDP / 162W PPT，满载发热接近两倍。67mm 级下压散热器压 9700X 比较轻松，压 9900X 就要更依赖风道和风扇曲线。
  • 性能预期：J3455 是 4C/4T Apollo Lake，9700X 单核大约提升 4-6 倍，多核提升一个数量级以上；9900X 相比 9700X 多核再强约 35-50%，但常驻 NAS 负载用不到这么高吞吐。
  • 最终选择：9700X。未来若确实需要更高 CPU 吞吐，AM5 仍可直接换 U。

硬件配置

价格为 2026 年 10 月参考区间，实际以渠道为准。机箱、6 块 6TB 机械盘、风扇、2 块 1TB SATA SSD、256GB 旧系统 SSD 尽量复用。

不买显卡、不买 NVMe、不买 96GB/192GB 内存，预算主要花在平台、存储路径和供电可靠性上。

内存计划

现有两条 16GB 内存必须先确认：

如果满足条件，直接插 DIMMA2 + DIMMB2 组双通道。32GB 初期分配建议：

后续升级路径：

  • 确实需要更多内存时，优先补同规格 2×16GB 到 64GB。
  • 或换 2×48GB 到 96GB。
  • 不建议 16GB 和 48GB 混插追求容量，稳定性排查成本不值。

主板选择与避坑

首选型号

关键是买 非 MAX 初版。已核对 WiFi 版规格，并经客服确认其扩展槽为一个 x16 和一个 x4。

项目 规格
板型 mATX，约 243.84 × 243.84mm

无 WiFi 版能不能买

可以买，而且如果便宜 100 元以上，无 WiFi 版更适合 NAS：

  • 正式网络使用有线 5G 网口。
  • Wi-Fi 只用于装机临时联网或应急，不能作为 7×24 存储服务的主网络。
  • 无 WiFi 版仍需确认规格没有被削减：双 PCIe 槽、4 SATA、3 M.2、5G LAN、支持 9700X。
  • 不能把 Mortar MAX WiFi 当成升级版购买，MAX 版砍掉第二 PCIe 槽。

板载 PCIE_PWR

B850M 追击炮有额外板载 8pin PCIE_PWR 供电口。无独立显卡、只插 ASM1166 时大概率不需要接；未来如果上显卡，必须按主板手册确认是否要求接入，不能把 EPS 8pin 和 PCIe 8pin 混用。

存储与 SATA 扩展

盘位规划

现有资产：

推荐跨控制器分布：

控制器 连接设备
主板原生 SATA 1TB SSD A、HDD 1、HDD 2、HDD 3
ASM1166 1TB SSD B、HDD 4、HDD 5、HDD 6、256GB SSD（稳定后可选）

这样有两个好处：

  • PVE 的 SSD mirror 跨主板控制器和扩展卡。
  • rsync 的数据盘/备份盘也尽量跨控制器，单张 ASM1166 故障不会同时打掉一对数据。

注意：因为一块 PVE SSD 在 ASM1166 上，不能把 ASM1166 整卡直通给 OMV。机械盘必须逐块按 /dev/disk/by-id 直通。装机后要专门测试拔掉 ASM1166 时，PVE 能否从原生 SATA 上的另一块 SSD 降级启动。

为什么暂时不买 NVMe

两块 1TB SATA SSD 做 ZFS mirror，对 PVE 系统、OMV/App/AI Gateway 的系统盘、Docker 镜像、模板和配置已经足够。当前网络出口和 HDD 数据吞吐不会成为 NVMe 的受益点。

后续如果确实出现高随机 I/O 的 VM、数据库或缓存需求，再考虑加 M.2 NVMe。它不是本次必须项。

256GB 旧系统盘怎么用

迁移期间不要动它，保留旧系统可回滚。新平台稳定 1-2 周后：

  • 若 SMART 健康且能稳定内置：做 PVE local backup、vzdump、ISO、VM 模板、临时测试 VM 和配置导出。
  • 若它仍是 USB SATA SSD：更适合退役或做救援安装盘，不适合继续承担 7×24 系统服务。
  • 不建议做 PVE 主系统盘、ZFS 第三成员、OMV 数据盘或唯一重要备份。

ASM1166 采购要求

ASM1166 不是 PCIe 4.0 扩展卡。它本质是：

插在 B850M 的 PCIe 4.0 x4 槽上，会协商为 PCIe 3.0 x2。对 6 块机械盘和网络存储足够。

购买时认准：

可关注系列：

  • GLOTRENDS SA3026C
  • MZHOU ASM1166 6 Port
  • StarTech 6 口 ASM1166 卡（通常偏贵）

避免：

  • ASM1066 / ASM1064 混标商品
  • JMB575 等 port multiplier 方案
  • Marvell 低端复用方案
  • x1 金手指缩水版
  • 廉价 RAID 卡

到货验证：

x2 正常；如果显示 x1，要么卡缩水，要么链路协商异常，需要排查后再接数据盘。

AI 方案：API-first，暂不买 GPU

结论

本次不买显卡。本地半高显卡的问题：

  • 20GB 级半高工作站卡价格高，二手也不便宜。
  • 显存上限仍跑不了更好的 32B/70B 全量模型。
  • 小机箱、半高、散热和供电限制明显。
  • 为了有限推理能力投入大量预算，收益不如外部 API。
  • API 可以随模型升级而升级，不需要本地换卡、维护 CUDA 和散热。

AI Gateway 虚拟机

API key 和管理界面不直接暴露公网，只通过受控反代或 VPN 访问。本地 CPU 只保留小模型兜底：

  • 3B/4B 模型
  • 7B/8B Q4 应急
  • embeddings
  • 离线小任务

未来重新考虑 GPU 时

优先看：

它是低功耗小卡，约 70W，通常不依赖额外显卡供电，适合未来低噪音 NAS 场景。但买前仍要确认：

  • 半高挡板
  • 插槽限长限高
  • 是否遮挡第二 PCIe 槽
  • 电源接口和线长
  • 40mm FLEX 电源噪音

不适合直接买全高 RTX 4000 Ada Generation 130W 版本，它和这个主板仓的散热、空间目标不匹配。当前阶段这些都只是未来备选，不进入采购清单。

电源选择

现有电源与尺寸风险

旧电源是 Enhance ENP-7025B 250W FLEX，长度约 150mm。机箱商品页只写「支持 FLEX 电源」并不等于支持所有长度的 FLEX。

常见 FLEX 电源本体尺寸：

Enhance ENP-7660B 品质好，但常见长度约 170mm。如果机箱电源仓刚好按 150mm 设计，它可能放不下。

首选电源

优点：

  • 长度与旧 7025B 一致。
  • 600W 余量足够覆盖未来 8 盘和低功耗半高显卡。
  • 单 +12V 输出，适合机械盘启动电流。
  • 比 250W 旧电源更能覆盖 9700X 峰值。

下单前仍要在商品页核对：

  • 三围是否明确写 150mm
  • 24pin、CPU 8pin/EPS、PCIe 6+2pin 数量
  • SATA 和大 4Pin 数量
  • 线长是否够走线
  • 12V 单路功率
  • 40mm 风扇噪音评价

备选

电源 结论
FSP 500W FLEX，如 FSP500-50FDB 系列 150mm 常见，无 GPU 方案够用，但未来余量小于 600W
Enhance ENP-7660B / 7660L 品质好，但约 170mm；只有实测电源仓余量足够才考虑
继续用 ENP-7025B 250W 不推荐，9700X + 多盘启动余量不足

功率预算

无 GPU 配置：

部件 估算
9700X 最高约 88W
主板 + 2×DDR5 + SSD + ASM1166 约 30-60W
6×3.5 英寸 HDD 稳态 约 35-70W
HDD 启动瞬时 可能额外增加 150-250W
风扇组 约 10-20W
整机稳态 约 150-230W
整机启动瞬时 约 280-380W

结论：

  • 400W 是底线。
  • 450-500W 是合理配置。
  • 600W 更适合未来 8 盘或低功耗半高显卡。
  • 旧 250W 必换。

供电注意：

  • 9700X 一个 8pin EPS 足够。
  • EPS 8pin 和 PCIe 8pin 不能混插。
  • SATA / 大 4Pin 不够时使用压接式转接线，不用劣质模压线。
  • 6 块 HDD 不要全挂在一条劣质一分多线上，尽量分散负载。
  • 所有 HDD 启动电流要按保守值估算，不依赖 hd-idle 或交错启动。

散热与机箱检查

散热器 高度 适用
利民 AXP120-X67 67mm 限高 ≥70mm 首选
ID-COOLING IS-55 55mm 高度紧张时备选
Noctua NH-L9a 37mm 极限矮仓兜底，性能预期最低

沿用现有风道：

  • 硬盘仓 4×12cm 风扇继续负责 HDD。
  • 主板仓 2×9cm 风扇继续负责 CPU、供电、内存和扩展卡。
  • 9700X 保持默认 65W TDP / 88W PPT，不追求 105W cTDP。

回家实测机箱时至少量：

  • 主板仓是否能容纳 244×244mm mATX。
  • CPU 散热器限高。
  • 内存马甲与散热器冲突。
  • 两条 PCIe 槽的物理开口位置。
  • ASM1166 半高挡板是否能对上开口。
  • FLEX 电源仓可用长度是否只有 150mm。
  • SATA 电源线和大 4Pin 转接头空间。
  • 2.5 英寸 SSD 固定位置。

Proxmox VE 架构

这次不再沿用「物理机 Ubuntu → KVM → OMV → Docker」的大杂烩，改为 Proxmox VE 作为宿主机。

实施原则：

  • PVE 只装 SSD mirror，数据 HDD 不建 qcow2。
  • HDD 逐块按 /dev/disk/by-id 直通给 OMV。
  • 同一块盘严禁同时挂载给 PVE 宿主机和 OMV VM。
  • ASM1166 上有 PVE SSD，因此不整卡直通 ASM1166。
  • App VM 不直接占数据盘，统一通过 OMV 的 NFS/SMB 挂载。
  • PVE 快照只用于系统回滚，不能替代数据备份。
  • 6 块 HDD 继续保留 rsync 1:1 策略。
  • BIOS 打开 SVM 和 IOMMU，安装后检查 IOMMU groups。
  • APT 源切换到 pve-no-subscription。
  • PVE / OMV 管理界面不直接暴露公网。
  • API Gateway 的 key、后台和日志入口不直接暴露公网。

装配前检查清单

  • 实测电源仓长度，确认是否只能放 150mm FLEX。
  • 量主板仓散热器限高，决定 AXP120-X67、IS-55 或 NH-L9a。
  • 确认 mATX 铜柱孔位和 244×244mm 主板空间。
  • 确认 B850M 追击炮是初版双 PCIe 槽，不是 MAX。
  • 若买无 WiFi 版，确认仍是 x16 + x4、4 SATA、3 M.2、5G LAN。
  • 确认第二 PCIe 槽物理开口与 ASM1166 半高挡板匹配。
  • 确认现有 2×16GB 是 DDR5 UDIMM，并查主板 QVL。
  • 检查 2×1TB SSD 和 256GB SSD 的 SMART、通电时长和写入量。
  • 核对 FX600-PT 商品页尺寸、接口数量和线长。
  • 准备 SATA 数据线、压接式电源转接线和 SSD 固定件。
  • BIOS 确认支持 9700X，并能开启 SVM/IOMMU。
  • 确认 UPS 支持 NUT，并规划 PVE 自动关机。

迁移计划

  1. 迁移前备份

    • 导出 OMV 配置、Docker Compose、Nginx、frp/DDNS 脚本、数据库 dump、证书和 SSH 配置。
    • 记录 6 块 HDD 的 SMART、序列号和分区/挂载关系。
    • 保留旧系统盘和至少一块备份盘不接入新机。

  2. 新平台最小安装

    • 只接 2×1TB SATA SSD，安装 PVE 并创建 ZFS mirror。
    • 先确认网络、BIOS、虚拟化和系统盘健康。

  3. 加入 SATA 扩展

    • 安装 ASM1166，用 lspci 确认 1b21:1166 和 x2 链路。
    • 按规划连接 HDD，先记录 by-id 和序列号。

  4. 恢复存储层

    • 创建 OMV VM，逐块直通 HDD。
    • 先只读挂载确认数据，再恢复 SMB/NFS/rsync。

  5. 恢复应用层

    • 创建 App VM，恢复 Docker Compose 和配置。
    • 应用统一挂 OMV 共享，不直接管理数据盘。

  6. 恢复 AI 层

    • 创建 AI Gateway VM。
    • 配置外部 API、路由、预算、日志和访问控制。
    • 可选配置小型 CPU Ollama 兜底。

  7. 观察与回收

    • 新平台稳定运行 1-2 周后再回收旧平台。
    • 旧系统盘确认不需要回滚后，再转为备份、ISO 或测试用途。

可靠性补强

  • UPS：通过 USB/NUT 联动 PVE 自动关机；路由器、光猫、交换机也纳入供电，否则远程链路会先断。
  • 备份层级：6 盘 rsync 继续承担本机双份；vzdump 只备份 VM 系统和应用配置；关键数据至少再保留一份离线或异地备份。
  • ZFS 健康：定期 scrub，关注 SSD/HDD SMART、ZFS pool 状态和替换流程。
  • 配置导出：所有 Compose、Nginx、PVE/OMV 配置进入私有 Git 或加密备份。
  • 硬盘体检：迁移前记录 SMART、通电时长和序列号；迁移后先只读确认，再启用写入任务。
