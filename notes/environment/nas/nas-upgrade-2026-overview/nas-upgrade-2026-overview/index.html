NAS 2026 升级总览
Yiwei Zhang 2026年11月15日 凌晨
3.8k 字 33 分钟 0 次   0 人   0 条
1794675600000

本文最后更新于：2026年11月17日 晚上

十月末新平台上线，十一月中旬旧机服务停机，升级周期两周。要做的事由旧机的状态决定：计算、内存、IO 接口、系统盘四项瓶颈同时出现，继续修补的成本高于更换。本文按实施顺序记录整个过程——每一步的现状、决策依据与结果，细节见各模块专文。

升级原因

旧机四个瓶颈各自独立又同时存在：CPU 与内存规格无法支撑更多虚拟机；新硬盘的接口规格与主板不匹配，存储扩容路径中断；系统盘容量小且型号老旧，系统组件已经多次出现空间告警。逐项更换硬件（换 CPU 需换主板、换主板牵动内存与接口）等于重建一台机器，因此决策为整机更换。新平台的形态在NAS 硬件升级方案中推导：虚拟化层用 PVE 9.2，原因是它是裸金属上开虚拟机的成熟方案，且 Web 管理面、集群、备份工具齐备；系统盘用双 SSD 组 ZFS mirror，原因有二：ZFS 的数据校验能发现静默损坏，mirror 保证任一盘故障时系统可继续运行。

平台搭建

安装一次成功。之后三天内出现连续崩溃，崩溃点不定。排查方法是控制变量：逐槽轮换内存，最终定位为某内存插槽与该批次内存条的兼容性问题，更换后故障不再复现。记录此事的原因在于它发生在平台早期，若误判为系统或硬盘问题，后续所有稳定性结论都会建立在错误前提上。

虚拟机划分为八台：存储、应用、网关、观测、家庭、开发、支撑、模板。划分依据是故障域与资源特征——数据库类服务内存占用大且需要独立调整，网关需要独立网卡配置，观测栈采集频率高但计算轻。VMID 与内网地址尾号保持一致，这是纯运维约定，目的是消除查表成本。两个配置项对所有虚拟机统一生效：

  • CPU 类型显式指定为 host：PVE 默认的 kvm64 档位不含 AVX 指令集，而 MongoDB 4.4 起要求 AVX，默认档位下数据库进程会直接退出
  • 数据盘配置 discard=unmap：虚拟机内 fstrim 释放的块通过 TRIM 穿透到宿主存储，否则删除文件后 ZFS pool 的实际占用不会下降，时间越长空间泄漏越大

两次资源调整在运行期完成：应用机内存 6G→10G（评论服务一次 OOM 后的定位结论），观测机 1G→2G（新观测栈的常驻需求），均为在线扩容。

备份一项核查出问题：VM 备份任务的调度器曾挂死，此后备份从未执行成功。处理方式不是立即修复，而是按既定决策归入搬盘批次统一处理——备份目标盘尚未迁移，此时修复备份链路得到的仍是到旧盘的备份。发现假就绪比没有备份更有害，因为前者会给出错误的安全感。

此阶段记录：基于 PVE 的 NAS 架构升级。

网络入口收敛

旧入口模式是一个服务一个公网端口。该模式的三个成本：每个端口都是独立攻击面；证书逐端口部署，续期依赖第三方服务，任一环节失败导致对应服务 HTTPS 报错；端口数量多导致安全组与转发规则难以审计。

收敛方案：全部 web 服务共用一个 HTTPS 端口，nginx 在 TLS 握手阶段读取 ClientHello 中的 SNI 字段决定转发目标。SNI 在握手明文阶段可读，因此不需要解密即可分发，后端全部走内网 HTTP。证书用通配符证书覆盖全部子域名，签发走 DNS-01 验证——家宽无 ICP 备案，80/443 端口被封，HTTP 验证不可行，DNS 验证通过域名托管商 API 增删 TXT 记录完成，续期由 acme.sh 定时任务自动执行。

DNS 侧用一条泛解析替代十几条子域名记录，新增子域名不再需要 DNS 操作。清理历史记录时发现一条仍被线上服务引用，删除前逐条验证引用成为固定流程。

非 HTTP 服务的处理：SSH 类服务保留独立端口（协议不走 SNI），WireGuard 走 UDP 端口提供远程内网访问，不新增任何服务暴露面。上线时排查过一个静默丢包问题，原因是容器化 WireGuard 新版将端口配置应用到了容器内实际监听口，而端口映射仍写旧默认口，入站包全部送到无人监听的端口，两端均无报错日志。最后验证 hairpin 回流：内网经公网域名访问全部子域名可达，内外地址一致。

此阶段记录：NAS 网关升级。

服务与数据迁移

迁移方法在两种之间选择：旧虚拟机整体镜像搬运，或逐服务新装最新版加数据迁移。选择后者的依据：旧镜像携带 EOL 系统组件（MongoDB 3.6 官方支持早已结束），搬运等于把淘汰版本带入新平台；逐服务迁移虽慢，但每个服务完成时版本欠账同时清零。第一个服务（评论）验证流程可行后，其余服务复制该流程。

各服务的迁移要点：

  • 评论系统：数据库 MongoDB 3.6→8.x 跨五个大版本，逻辑导出导入。环境对齐后暴露四个问题，各有明确机理：登录签名钥在旧环境静默借用数据库密码，环境变量逐项对齐时该借用关系断裂，管理端登录失效；服务端每个请求向境外的社交登录列表端点发起请求，境内访问延迟叠加导致全部接口变慢；存量评论头像 URL 指向境外源，需批量改写；反向代理缺端口头，管理端按默认 443 拼接 API 地址，请求发向不存在的端口。逐项修复后管理端加载稳定在两秒内
  • 访问统计：跨两个大版本。两个数据问题需要处理：新版会话模型会重建旧数据，逐表核对确认是合并语义而非丢失；新栈上线使用的备份存在快照时间差，切换前数日的访问记录仅在旧库，按时间区间导出、手工映射列名、幂等写回
  • 图床：四十余 GB 文件走局域网直传。难点在引用替换：全站一万七千余处地址存在"双端口形态"变体，直接批量替换会让变体残留并在后续替换中滚雪球，因此先扫描归一变体再统一替换，替换后全站产物扫描归零确认
  • 一言：服务版本为上游终版无需升级，问题在语料同步源被墙导致一万一千余句数月未更新，换镜像源后恢复
  • 静态站：Hexo 跨一个大版本，升级后在沙箱全量生成并与线上两千余页逐页对比，一致后切换；站内搜索从 27MB 单文件索引改为分片索引；发布流程收敛为单命令
  • 网盘：跨四个大版本。逐版本升级路径长且每步有数据迁移风险，改为全新安装加数据导入，文件级对账加密码哈希算法差异的回填处理，家人端无感
  • 家庭相册：三个库按特性分别迁移——MySQL 逻辑导出导入（对账用精确计数，存储引擎的行数估计值与真实值有偏差）；MongoDB 文档逻辑还原；MinIO 对象走 tar 管道直传，两千对象逐一对账，差额为对象存储内部临时文件
  • 服务裁撤：三个使用记录趋近于零的服务（知识库、笔记、同步观影）不迁移。每个被裁服务需清理四处痕迹：框架容器、网关路由、监控项、旧机实例，残留任何一处会产生空转容器或永久告警。数据 dump 归档，回滚成本为半小时回放
  • 旧机台账：三十余项现役组件逐一定性（延续/消亡及去向），同时修正两处历史文档误判

此阶段记录：服务迁移记录。

观测与告警

迁移期间变更频繁，出问题需要区分"变更引起"还是"原本存在"，这要求有变更前后的指标对比——观测栈因此在迁移完成前部署。结构：每台机器运行 node_exporter，ZFS 无现成指标的部分用 textfile collector 自产；Prometheus 保留三十天数据覆盖一个变更周期；拨测三十项覆盖虚拟机、服务、底层组件与公网链路，按各服务真实响应码配置基线；宿主机硬件心跳为 push 型，判断逻辑在本地执行，任一阈值越界则本轮静默，两分钟无心跳即告警——判断本地化避免了把阈值逻辑和硬件数据暴露在公网。对外提供公开健康页，脱敏在采集层完成（relabel 白名单过滤、instance 改写、设备名映射），公网管道中不存在未脱敏数据。

此阶段记录：自建观测栈。

工程治理

迁移暴露的维护成本集中在三处，对应三个治理动作：

  • 配置分散在各机器上，任何一台故障后配置不可恢复——二十六个服务的配置各自成独立 Git 仓集中托管，数据与密钥排除在外，每日凌晨快照比对漂移，漂移即意味着有人绕过流程改了配置
  • 发布流程五步手工操作，步骤遗漏会导致线上与源码不一致——收敛为单命令，构建、索引、同步、部署串联执行
  • 密钥散落在配置与文档中——集中到仓外加密档案，页面泄露过的恢复码全部轮换

此外迁移全程以编号工作记录加活状态 README 承载决策过程，每个决策可回溯到当时的约束条件。

此阶段记录：升级背后的工程治理。

旧机退役

迁移完成的服务按依赖顺序分批停机：先停应用层（评论、一言、统计），再停旧网关与旧监控，最后清理裁撤服务残留与定时脚本。每批停机后执行全站回源验证，十项核心服务全部正常后进入下一批。旧机仅存三类等待搬盘批次：数据未迁的小服务、备份链、公网 DDNS，机械盘迁移完成后整机下线。

小结

两周内完成平台重建、网络收敛、服务迁移、观测部署与治理沉淀。产出不只是硬件更换：每个服务版本归零、每项配置入仓、每个决策有记录，后续维护成本相应下降。剩余工作为机械盘数据迁移，完成后旧机下线。
