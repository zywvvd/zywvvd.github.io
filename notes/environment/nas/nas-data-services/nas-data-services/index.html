服务迁移记录：博客部件与家庭数据的搬家
Yiwei Zhang 2026年11月15日 凌晨
3.3k 字 28 分钟 0 次   0 人   0 条
1794672600000

本文最后更新于：2026年11月16日 晚上

旧 NAS 退役进入倒计时，上面跑着的服务要逐一搬进新平台：既有博客的评论、统计、图床、一言这些页面背后的服务，也有家人的网盘和相册，还有几个装上之后没人用的。本文记录这次服务迁移的全过程——每个服务原来什么样、怎么搬的、路上挖出什么问题，以及哪些服务决定不搬、直接退役。

背景：旧机上都跑着什么

博客这一侧有五个后台服务。 博客页面本身是静态的，托管在 GitHub Pages 上，但页面背后有一批服务长期跑在旧 NAS 上：读者在文章底部留言，走的是评论系统，它的数据库 MongoDB 还是五年前装的 3.6，官方支持早已结束；每次访问被统计系统记一笔；文章里的每一张配图都从旧机的图床加载——六年积累下来四十余 GB，散布在各篇文章里的引用有一万七千多处；页脚的随机短句来自自建的一言服务；首页的背景视频靠一个壁纸配对接口。这些服务只要有一个下线，博客对应的部位就立刻失灵——旧机停机之前，必须把它们全部安置好。

家庭这一侧是网盘和相册，外加几个没人用的。 网盘是 Nextcloud，家人日常存照片和文档，但它已经带着 503 的病跑了半年；相册是自部署的三容器联动系统——MySQL 关系库存成员和事件、MongoDB 文档库存元数据、MinIO 对象存储放图片本体。这两个是家人真实在用的数据，搬家不能丢、访问不能断。此外还有知识库、笔记、同步观影三个服务，部署一年多，使用记录趋近于零。

旧机停机之前，这些服务要么搬走，要么退役，都得有个交代——这就是本次迁移的全部内容。

目的

定四条验收标准：

  • 博客的五个服务全部运行在新平台，数据零丢失——评论逐条计数一致，统计事件逐条核对，图床逐字节同步
  • 版本全部升到最新：数据库、服务端、静态站，五年没升级的欠账一次还清
  • 家庭数据完整迁移，家人访问无感——地址不变、数据不丢
  • 没人用的服务在迁移前退役，不把包袱带进新家

方案：逐个新装，先做减法

博客服务采用"逐个新装 + 数据迁移"，而不是把旧机整体镜像搬过来。 整体镜像快，但会把老旧的系统和五年的积弊原样带到新平台——MongoDB 3.6 这种连官方支持都已结束的版本，正是最不该带走的部分。所以每个服务都在新平台直接安装最新版，再把数据迁移进去：评论的数据库从 3.6 直升 8.x，跨过五个大版本；统计跨两个大版本；评论服务端补上一年的版本差。第一个服务验证这套流程可行之后，后面的照方抓药。

家庭侧先做减法。 每个服务问三个问题：还在用吗？数据需要留吗？新平台值得给它位置吗？知识库、笔记、同步观影三个答案一致——没人用、数据可归档、不值得，直接退役。网盘和相册是家人真实数据，照常迁移（网盘跨四个大版本的取舍，已并入升级总览）。

退役放在迁移之前做，理由很直接：搬家的成本和服务数量成正比，少搬三个，就少三份配置、三份监控、三条路由、三次对账。

实施

评论系统是其中最复杂的一个。 数据库 MongoDB 从 3.6 直升 8.x 跨五个大版本，服务端程序补上一年的版本差，一千余条评论逐条计数对齐。数据搬完，问题才开始暴露：先是管理后台完全登不进去，排查发现登录签名钥在旧配置里一直静默借用数据库密码，环境变量对齐时这一项被漏掉；修好登录，后台又要加载数秒才响应——原因是服务端每个请求都会替访客去境外拉一份社交登录列表，关掉这个行为后加载回到两秒内；同类的问题还有两个：存量评论头像全部指向境外图源，反向代理少配了一个端口头，管理端把接口请求打到不存在的默认端口上。四个问题逐个修完，这个五年没动过的服务才算真正在新家站稳。前端评论组件也顺手改为自托管构建——此前一次主题升级时第三方 CDN 悄悄换了构建格式，评论区断过一次，这次把这个外部依赖彻底去掉。

访问统计的关键是数据不能有缺口。 服务跨两个大版本升到最新，四十六万条事件全量落位。期间有两个容易误判的地方：新版会话模型会重建旧数据，面板上看起来"变少了"，逐表核对确认是合并而非丢失；新平台上线用的是几天前的备份，切换前最后几天的访问还留在旧库——按时间区间从旧库导出，跨版本手工映射列名后幂等写回，切换期的数据一条不缺。

图床的难点不在搬家在换引用。 四十余 GB 文件走局域网管道直传即可，但全站一万七千余处图片地址都指向旧机，要全部替换到新地址。先扫描出"双端口形态"的地址变体——这种变体如果不先归一，批量替换后残留会越滚越多；替换完成后全站产物再扫描一遍，归零确认；最后给图床补上跨域响应头，站内搜索索引等跨域场景一并打通。

一言的问题不在服务在语料。 服务版本已是上游终版，无需升级；真正的问题是一万一千余句语料的同步源被墙，几个月没有更新——换成可达的镜像源后恢复自动同步，服务本身零改动。

静态站本体也顺手升了级。 Hexo 跨一个大版本升级，先在沙箱里全量生成，与线上两千余页逐页对比一致后才切换；站内搜索从 27MB 的单文件索引重构为分片索引（详见 Fluid -48）；发布流程收敛为一条命令。

家庭相册三个库，各迁各的。 关系库（MySQL）逻辑导出导入，对账时行数"对不上"，排查发现是存储引擎的近似估计特性，改用精确计数查询后逐表相等——教训是对账永远用精确查询；文档库（MongoDB）几百个文档逻辑还原，零失败；对象存储（MinIO）两个 GB 走 tar 管道直传，两千个对象逐一对账，差额十几个是对象存储自身的内部临时文件，会自动清理，不属于用户数据。迁移完成后前端切换新域名，手机 App 走接口通路实测一致，旧栈的六个容器停机留档，需要回滚时一条命令即可恢复。

退役的服务清理要彻底。 每个被退役的服务在四个位置留有痕迹：新平台的框架容器、网关的路由块、监控项、旧机上的实例，全部清掉才算干净——漏掉任何一处，要么留一个空转的容器，要么留一个永远告警的监控。数据 dump 全部归档留底：反悔的成本是半小时回放，比留一套没人用的服务常年运行便宜得多。

收尾给旧机做了次全量对账。 旧机上三十余项现役组件逐一定性：延续的标注新平台上的位置，消亡的写明原因，形成退役台账。顺带勘误了两处历史文档的误判——一个被记成"自研服务"的其实是第三方引擎，一个被记成"已停用"的其实还活着。对账的价值不止在迁移，也在于修正自己的记录。

结果

对照目的逐条验收：

  • 博客五个服务全部运行在新平台，旧机对应服务已停机 ✓
  • 数据零丢失：评论逐条计数一致；统计四十六万事件核对一致，切换缺口补回；图床逐字节同步；相册三库与网盘对账一致，家人端无感切换 ✓
  • 版本全部最新：评论服务端补一年、数据库跨五个大版本、统计跨两个大版本、静态站跨一个大版本 ✓
  • 三个闲置服务退役，数据归档留底 ✓
  • 旧机三十余项组件全部定性，退役按台账执行 ✓

过程中额外的收获是排掉了一批"一直坏着但没人发现"的问题：评论系统四处、统计同步源一处、搜索脚本一处——都是环境对齐和全量对账时才暴露的。最终的验证方式很直接：旧服务器逐项停机后，全站和家人数据回源实测，一个字节不受影响。

尾声

这次迁移沉淀下来的经验：对账要用绝对数和精确查询，"差不多"不叫对账，估计值不作数；切换期的数据缺口要显式补，那是最容易被忘掉的一批数据；环境对齐的过程就是体检，暗病都会在搬家时暴露；前端引用切完要回源验证，缓存会骗人；退役要赶在搬家之前，少搬一个就少养一个。数据迁移的较真不在技术，在口径——迁移时多较真一次，退役时就少一次犹豫。
