数据迁移与服务裁撤：家庭数据搬家记
Yiwei Zhang 2026年11月15日 凌晨
1.4k 字 12 分钟 0 次   0 人   0 条
1794672600000

本文最后更新于：2026年11月14日 上午

服务迁移做到后半程会发现一个事实：不是所有服务都值得搬。家庭数据这一批的特点是数据量小但种类杂——网盘要跨版本、相册三库联动，还有一批"部署满一年发现根本没人用"的服务。本文记录这一批的迁移取舍、三库对账的方式，以及"先做减法再搬家"的裁撤执行。

背景：杂而小的一批

NAS 架构升级进入数据面时，旧机上还挂着三类东西：一个带病的自建网盘（Nextcloud 31，503 半年）；一套家庭相册服务（自部署的三容器联动系统，关系库存成员事件、文档库存元数据、对象库存图片本体）；以及知识库、笔记、同步观影这几个部署后使用记录趋近于零的服务。它们和博客服务不同——博客五部件是每天被访问的活器官，这一批是"家人的数据和没人用的存量"。

目的

三条：家人数据（网盘、相册）零丢失进新栈且家人无感；没人用的服务在迁移前裁掉，不带包袱进新家；旧机上所有服务完成定性——每个要么有明确去处、要么有明确死因，形成退役台账，不留"好像还有个什么东西在跑"的糊涂账。

方案选择：先做减法

每个服务过三问：还在用吗？数据有吗？新栈值得给它一个位置吗？知识库、笔记、同步观影三个答案一致——没人在用、数据可归档、不值得。裁掉。网盘和相册是家人真实数据，必迁。网盘的版本取舍（跨四版本升级 vs 全新安装）单独立篇记录了，见 Nextcloud 迁移实录；本文记录相册三库和裁撤执行。

裁撤为什么要在迁移前做：搬家的成本和服务数量成正比——少搬三个，就少三份配置、三份监控、三条路由、三次对账。断舍离的最佳时机永远是搬家前。

实施

相册三库联动，各迁各的。 三个库三种特性，迁移方式各不相同：

  • 关系库（MySQL）：逻辑导出导入。对账时踩了个坑——行数"对不上"，排查发现是存储引擎的近似估计特性，精确计数查询后逐表相等。教训：对账永远用精确查询，估计值不作数
  • 文档库（MongoDB）：几百个文档逻辑还原，零失败
  • 对象存储（MinIO）：两个 GB 走 tar 管道直传，两千个对象逐一对账——差额十几个是对象存储自己的内部临时文件，会自清理，非用户数据

迁移后前端切新域名，手机 App 走 API 通路实测一致，旧栈六容器停机留档（回滚 = 一条命令）。

裁撤执行，一条链路四处清。 每个被裁服务在新栈框架容器、网关路由块、监控项、旧机实例四个位置都有痕迹，全部清掉才算干净——漏掉任何一处，要么留一个空转的容器，要么留一个永远告警的监控。数据 dump 全部留档：反悔的成本是半小时回放，比留一套没人用的服务常驻运行便宜。

旧机全量对账定版。 收官前给旧机三十余项现役组件逐一定性：延续的标注新栈位置，消亡的写清死因。顺带勘误两处历史文档误判——一个被记成"自研服务"的实为第三方引擎，一个被记成"已死"的其实还活着。对账的价值不止在迁移，也在修正自己的认知。

结果

  • 家人数据：网盘 + 相册全部落位新栈，对账一致，家人端无感切换 ✓
  • 减法成果：三个服务全链路下线，数据 dump 归档 ✓
  • 台账：旧机三十余项全部定性完毕——后续退役按台账执行即可 ✓

旧机此后只剩音乐库、网盘工具、记事本这几个还带真实数据的服务，等机械盘搬迁时一并归位。

尾声

这一批做完最深的体会：数据迁移的较真不在技术上，在口径上——精确计数、逐项对账、每个差异都要有解释。迁移时多较真一次，退役时就少一次犹豫。
