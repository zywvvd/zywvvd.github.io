Fluid -47- 主题升级至 v1.9.9
Yiwei Zhang 2026年11月11日 晚上
4.8k 字 41 分钟 0 次   0 人   0 条 ?
1794400200000

本文最后更新于：2026年11月12日 上午

主题 fork 自 2021 年 8 月，此后没有跟上游同步过。这次把上游累计的 52 个提交合并进了个人版本，冲突只有 2 个文件；顺手把 53 个无语义的提交重写成 10 个功能提交，又清了几处积年的代码欠账。本文记录升级、历史重写与重构的过程。

新版本带来什么

上游这 52 个提交（v1.9.7 基线 → v1.9.9，2026-03 发布）里，对我有实际价值的：

原生 Umami 统计插件（#1055，umami-view.js）

我自己写过一个 pvuv 取数外壳（vvdpostpvuv）：主题渲染计数占位元素，页面脚本向自建的 pvuv 服务请求 Umami 统计数据再回填。上游这次把同类能力做成了主题原生插件——统计来源在主题配置里直接切换，不再依赖自建服务的可用性。

一批确定性修复

  • 进度条无限加载（#1067）
  • 移动端越界元素隐藏
  • Giscus 背景不透明
  • Google Analytics 配置判断

Canonical URL 支持（#1038）——SEO 基础项。

版本状态：v1.9.9 为 2026-03 发布的稳定版，合入后主题回到上游主线，后续同步成本从「五年一跳」降为「常规合并」。

升级后的实际好处

  1. 文章计数双模式：vvdpostpvuv（自建 pvuv 服务取数）与 umami（上游原生插件）作为并列分支共存于主题模板，主题配置 post.meta.views.source 一行切换
  2. 上游修复带入：进度条、移动端、GA 判断等
  3. 后续升级恢复常规 merge：基线对齐后，上游更新直接合并跟进
  4. SEO 增强：Canonical URL 支持

升级过程

盘点：先量化分叉

fork 维护最怕的不是改代码，是不知道自己改过什么。GitHub 的 compare 接口可以直接量化：

返回 status: diverged——两侧各有对方缺失的提交：fork 侧 53 个自定义提交，上游侧 52 个新提交（v1.9.7 → v1.9.9 两个版本发布）。

再拉一次文件级 diff（git diff upstream/master HEAD --stat）确认改动面：67 个文件，+879/-1100 行，集中在 layout/_partials、source/js、languages——没有结构性大改，合并可行。

合并：冲突只有 2 个文件

  • layout/_partials/post/meta-top.ejs：fork 侧的 vvdpostpvuv 渲染分支与上游新增的 umami 渲染分支落在同一段 if/else 链——两个分支都保留，主题配置 post.meta.views.source 决定实际生效的来源

其余 65 个文件全部自动合并，无需干预。

升级后效果

重新生成全站并逐项验证：

  • 文章页：视频背景、看板娘、TOC、pvuv 计数（「阅读 1 次」）全部正常
  • 地球统计页（301 行自定义布局）：planetary.js 地球、30 天来访者渲染完好
  • 搜索框、打赏、导航菜单：无回归

提交历史重构：53 个自定义提交折叠为 10 个功能提交

合并之后干了一件事：把 fork 侧 53 个自定义提交（多数提交消息为无语义的 “update”，其中 1 个还拼错了）重写为 10 个语义化的功能提交，并强推替换了远端历史。

为什么要重写

翻了一下 fork 的提交历史，53 个自定义提交里：

  • 有清晰语义的不到 10 个：add-post-pv-uv、upspeed-local-search、add-reward、add-hefeng-weather、close-lazy-load-mathjax、update-url-to-https……
  • 其余全是 update、update、udpate（还拼错了）、再 update

这些 “update” 提交单个都无害，但堆在一起让 git log 变成了考古现场：想找「我当时是怎么加打赏的」，得逐个 diff 才知道。趁这次大版本升级，一并清算。

前提：先合并、再重写

顺序很重要。如果先重写历史再合并上游，两边的历史会更难对齐。正确顺序是：

  1. 先把上游 v1.9.9 合并进来（冲突该解就解）——此时 fork 历史完整保留
  2. 在合并结果上做历史重写——重写只影响「提交的形状」，不影响「内容的终态」

方法：clean 分支重放

核心思路：以最终状态的文件为准，按功能分组从终态「摘取」文件，在干净基线上重新提交。旧历史不参与，只做终点对照。

第 4 步是整個方法的基石：只要这个 diff 为空，就证明重写没有丢失任何内容——旧历史里的每一行改动都在新历史的某个提交里。验证通过后才切换分支、强推：

重写前后的对照

三条经验

  1. 空 diff 是唯一可信的验收。重写历史的一切操作，最终都要落到「新旧终点 tree 完全一致」这一条验证上。中间过程错了多少次都无所谓，终点不对就重来。
  2. 保险分支先行。动手前先 git branch backup/old-history——强推后旧提交在远端会变成孤儿，本地分支是唯一的恢复来源。
  3. 提交消息是给自己看的文档。当年几十个 “update” 省下的 30 秒，这次花了一小时考古找回来。语义化提交不是仪式感，是给未来的自己留的路标。

代码重构：清掉几年的欠账

历史干净了，代码本身也到了还账的时候。这次升级前后，把主题里几处一直别扭的实现一并重做了——分布在主题仓和站点仓两个仓库。

视频背景注入重写

首页的动态视频背景是早期写的，注入脚本在站点侧 source/_inject/header.ejs（fluid 的 inject 机制挂进每个页面）。旧实现能跑，但欠账不少：

  • 依赖 jQuery：封面降级用 $.getJSON，为此单独加载一份 jQuery
  • innerHTML 拼 HTML："<video src=" + video_url + " autoplay>" 这样拼字符串，URL 没转义也没引号包裹
  • JS 手算尺寸：读 body.clientWidth/Height 算宽高比，再 setAttribute 调整 video 宽高
  • UA 嗅探：正则匹配 iPad/iPhone/Android 判断移动端
  • 隐式全局变量：video_url、banner_obj 等全是裸赋值

重写后：

  • video/img 元素用 createElement + 属性赋值生成，不再拼 HTML 字符串
  • 尺寸适配交给 CSS：position: fixed + object-fit: cover，整个 set_video_attr 函数删掉
  • 播不播视频的判断改用 matchMedia：prefers-reduced-motion（动画敏感用户）、pointer: coarse（触屏）、innerWidth < 768，任一命中只显示封面图——比 UA 嗅探可靠，也照顾了该关动画的人
  • 封面图直接用 video 的 poster 属性，替代手叠的 img 层
  • 双源降级链保留：壁纸配对 API 失败后落到本地 video_url.json

文件从 104 行降到 91 行，行数变化不大，但 jQuery 依赖、字符串拼接和 UA 嗅探这三笔老账都清了。

中途还踩了自己挖的坑：样式表里视频层选择器写成 #vvd-bg-video，实际元素 id 是 #video_item——z-index 规则没挂上，视频层把 footer 盖住了。一行修正。

地球统计页数据链换 fetch

地球访客统计页（earth_sta 布局）的数据加载还是 XHR + $.parseJSON，脚本里还躺着一段加载 demo 地震数据、弹 alert 的死代码。统一换成 fetch + JSON.parse，死代码删除，页面从 301 行减到 294 行。

文章计数脚本提取

文章页的 PV/UV 计数原来是一段内联脚本。提取成独立文件 source/js/vvdpostpvuv.js，经 fluid 的 import_js 机制挂载——和上游 umami-view.js 的组织方式对齐。

导航站脚本整理

本地导航站页面（site_map 布局）的截图数据提交从 $.post 换成 fetch + URLSearchParams——请求体保持表单编码格式，服务端无感。地球页和导航站的外链脚本（planetary.js 全家、jQuery、demo.js）原来都是渲染阻塞的同步 script，统一加了 defer，内联初始化包进 DOMContentLoaded：defer 脚本按文档顺序在 DOMContentLoaded 之前执行，依赖链不受影响，首屏渲染不再被这些脚本卡住。

搜索的重构

站内搜索的 Pagefind 重构（27MB XML → 分片索引）独立成篇，见《Fluid -48- 基于 Pagefind 重构站内搜索》。

尾声

这些重构都是在重写后的干净基线上做的：每处改动一个独立提交，git log 里一眼可查。历史重写给的不只是好看的记录，是往后每一次改动的落点。
